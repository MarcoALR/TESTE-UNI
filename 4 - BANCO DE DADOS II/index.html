Os três JOINs, lado a lado

1 · INNER JOIN — só o que casa dos dois lados

SELECT c.nome, p.num_pedido, p.valor_pedido
  FROM cliente c
 INNER JOIN pedido p ON c.codcliente = p.codcliente;
Resultado — 3 linhas
nomenum_pedidovalor
ANA10100,00
ANA11250,00
BRUNO1280,00
CARLA não aparece — não tem pedido
Leia assim "Me dê os clientes que fizeram pedido." Quem não casou nos dois lados some do resultado. Repare que a ANA aparece duas vezes: o JOIN repete a linha da esquerda uma vez para cada correspondência da direita.

2 · LEFT JOIN — tudo da esquerda, mesmo sem par

SELECT c.nome, p.num_pedido, p.valor_pedido
  FROM cliente c
  LEFT JOIN pedido p ON c.codcliente = p.codcliente;
Resultado — 4 linhas
nomenum_pedidovalor
ANA10100,00
ANA11250,00
BRUNO1280,00
CARLANULLNULL
A regra de ouro do LEFT JOIN Toda linha da tabela da esquerda aparece. Quando não há par na direita, o Oracle preenche com NULL. É por isso que LEFT JOIN é a ferramenta de "quem NÃO tem": 
SELECT c.nome
  FROM cliente c
  LEFT JOIN pedido p ON c.codcliente = p.codcliente
 WHERE p.num_pedido IS NULL;   -- clientes que nunca compraram → CARLA

3 · RIGHT JOIN — tudo da direita, mesmo sem par

Para o RIGHT JOIN fazer diferença, precisamos de uma tabela da direita com sobra. Use PRODUTO, onde o BRINDE nunca foi vendido:

SELECT i.num_pedido, pr.descricao, i.quantidade_item
  FROM item_pedido i
 RIGHT JOIN produto pr ON i.codproduto = pr.codproduto;
Resultado

O atalho que resolve metade das questões RIGHT JOIN é o LEFT JOIN com as tabelas trocadas de lugar. Estas duas consultas devolvem exatamente o mesmo resultado: 
FROM item_pedido i RIGHT JOIN produto pr ON ...
FROM produto pr LEFT JOIN item_pedido i ON ...
Na prática quase ninguém usa RIGHT — inverte-se a ordem e usa LEFT, que é mais fácil de ler. Mas na prova você precisa saber que existe e explicar a diferença.

As duas sintaxes — o professor é Oracle

Vale conhecer as duas porque as duas já apareceram em material de Oracle:

ANSI (moderna) — use esta

SELECT c.nome, p.num_pedido
  FROM cliente c
  LEFT JOIN pedido p
    ON c.codcliente = p.codcliente
 WHERE p.valor_pedido > 50;

Junção no ON, filtro no WHERE. Separado e claro.

Oracle antiga, com (+)

SELECT c.nome, p.num_pedido
  FROM cliente c, pedido p
 WHERE c.codcliente = p.codcliente(+)
   AND p.valor_pedido > 50;

O (+) fica no lado que pode faltar. Aqui vira um LEFT JOIN.

Como não confundir o (+) O (+) marca o lado incompleto — aquele que vai receber NULL. Então:
  • c.codcliente = p.codcliente(+) → mantém tudo de CLIENTE = LEFT JOIN
  • c.codcliente(+) = p.codcliente → mantém tudo de PEDIDO = RIGHT JOIN
Decore: "o (+) fica do lado que tem buraco". E o Oracle não aceita (+) dos dois lados — para FULL OUTER JOIN só existe a sintaxe ANSI.

Juntando mais de duas tabelas

É só encadear. Cada novo JOIN liga com alguma tabela já presente:

SELECT c.nome,
       p.num_pedido,
       pr.descricao,
       i.quantidade_item,
       i.quantidade_item * i.preco_unitario AS total_item
  FROM cliente c
 INNER JOIN pedido p       ON c.codcliente = p.codcliente
 INNER JOIN item_pedido i  ON p.num_pedido = i.num_pedido
 INNER JOIN produto pr     ON i.codproduto = pr.codproduto
 ORDER BY c.nome, p.num_pedido;
Receita para montar qualquer JOIN em 4 passos
  1. Quais tabelas têm as colunas que o enunciado pediu? → entram no FROM/JOIN
  2. Qual coluna liga cada par? → é a PK de uma com a FK da outra, vai no ON
  3. O enunciado diz "todos"? Se sim, é LEFT (ou RIGHT); se diz "que têm", é INNER
  4. Filtro extra ("acima de", "no ano de") vai no WHERE, não no ON
Os quatro erros que mais tiram nota na aberta
  • Esquecer o ON. Sem ele o Oracle faz produto cartesiano: 3 clientes × 3 pedidos = 9 linhas sem sentido. Em sintaxe antiga, o mesmo acontece se faltar a condição no WHERE.
  • Pôr o filtro no WHERE quando é LEFT JOIN. Escrever LEFT JOIN pedido p ON ... WHERE p.valor_pedido > 50 mata o LEFT: a Carla tem valor NULL, NULL não é maior que 50, e ela some — a consulta vira um INNER disfarçado. Se o filtro é sobre a tabela opcional, ele vai dentro do ON.
  • Não usar apelido (c, p, i). Com duas tabelas tendo preco_unitario, o Oracle acusa column ambiguously defined.
  • Trocar a ordem no LEFT. A tabela que você quer inteira tem que estar no FROM.

Modelo de resposta para a aberta

Se pedirem para explicar e exemplificar os três JOINs, responda nesta ordem:

O que é um JOIN. É a operação que combina linhas de duas ou mais tabelas a partir de uma coluna em comum — normalmente a chave primária de uma com a chave estrangeira da outra. A condição de junção é escrita na cláusula ON.

INNER JOIN. Retorna apenas as linhas que têm correspondência nas duas tabelas. Se um cliente não tem pedido, ele não aparece no resultado.

SELECT c.nome, p.num_pedido
  FROM cliente c
 INNER JOIN pedido p ON c.codcliente = p.codcliente;

LEFT JOIN. Retorna todas as linhas da tabela da esquerda (a do FROM), mesmo sem correspondência. Nesse caso as colunas da tabela da direita vêm preenchidas com NULL. Serve para listar, por exemplo, todos os clientes incluindo os que nunca compraram.

SELECT c.nome, p.num_pedido
  FROM cliente c
  LEFT JOIN pedido p ON c.codcliente = p.codcliente;

RIGHT JOIN. É o inverso: retorna todas as linhas da tabela da direita (a do JOIN), preenchendo com NULL as colunas da esquerda quando não há par. Serve para listar todos os produtos, inclusive os que nunca foram vendidos.

SELECT i.num_pedido, pr.descricao
  FROM item_pedido i
 RIGHT JOIN produto pr ON i.codproduto = pr.codproduto;

Observação final. O RIGHT JOIN equivale a um LEFT JOIN com as tabelas invertidas. No Oracle também existe a sintaxe antiga com o operador (+), colocado do lado que pode não ter correspondência.

Treine antes da prova

1. Liste o nome de todos os clientes e o valor total de pedidos de cada um, incluindo quem nunca comprou. 
SELECT c.nome, NVL(SUM(p.valor_pedido), 0) AS total
  FROM cliente c
  LEFT JOIN pedido p ON c.codcliente = p.codcliente
 GROUP BY c.nome
 ORDER BY total DESC;

Por que LEFT: o enunciado diz "incluindo quem nunca comprou". O NVL troca o NULL do SUM por 0.

2. Liste os produtos que nunca foram vendidos. 
SELECT pr.codproduto, pr.descricao
  FROM produto pr
  LEFT JOIN item_pedido i ON pr.codproduto = i.codproduto
 WHERE i.codproduto IS NULL;

O padrão: LEFT JOIN + WHERE <coluna da direita> IS NULL = "quem não tem".

3. Liste nome do cliente, número do pedido e forma de pagamento, só dos pedidos de 2025. 
SELECT c.nome, p.num_pedido, tp.descricao AS pagamento
  FROM cliente c
 INNER JOIN pedido p          ON c.codcliente = p.codcliente
 INNER JOIN tipo_pagamento tp ON p.cod_tipo_pagamento = tp.cod_tipo_pagamento
 WHERE EXTRACT(YEAR FROM p.data_criacao) = 2025;

Por que INNER: "só dos pedidos" — quem não casa não interessa.

4. Qual a diferença de resultado entre colocar o filtro no ON e no WHERE num LEFT JOIN? 
-- filtro no ON: a Carla CONTINUA aparecendo (com NULL)
  FROM cliente c
  LEFT JOIN pedido p ON c.codcliente = p.codcliente
                     AND p.valor_pedido > 50;

-- filtro no WHERE: a Carla SOME, vira um INNER disfarçado
  FROM cliente c
  LEFT JOIN pedido p ON c.codcliente = p.codcliente
 WHERE p.valor_pedido > 50;

Esta é a melhor resposta que você pode dar se a aberta pedir "comente a diferença". Mostra que você entendeu o mecanismo, não só decorou.

Por que é tão cobrado WHERE campo = NULL não dá erro — devolve zero linhas, em silêncio. É o tipo de bug que passa despercebido, e por isso vira questão. Vale também para <> NULL.

As quatro afirmações falsas da questão 9
  • "HAVING é aplicada dentro do WHERE" — falso: HAVING vem depois do GROUP BY.
  • "SUM, MAX e HAVING são funções agregadas" — falso: HAVING não é função, é cláusula. As agregadas são COUNT, SUM, MAX, MIN e AVG.
  • "GROUP BY controla a ordem das tuplas" — falso: quem ordena é o ORDER BY.
  • "eliminar duplicação é o padrão, DISTINCT é facultativo" — falso: o padrão é manter as duplicatas.
A verdadeira era: COUNT(*) conta o número de tuplas que satisfazem as condições.
WHERE × HAVING WHERE filtra linha por linha, antes de agrupar. HAVING filtra grupos, depois de agrupar — é o único lugar onde se pode usar função agregada como condição. 
SELECT c.cidade, COUNT(*) AS qtd
  FROM cliente c
 WHERE c.limite_valor > 1000      -- filtra CLIENTES
 GROUP BY c.cidade
HAVING COUNT(*) > 1               -- filtra CIDADES
 ORDER BY qtd DESC;
A regra que derruba a questão 12 Toda coluna do SELECT que não está dentro de função agregada precisa estar no GROUP BY. E o contrário também cai: não se coloca função agregada dentro do GROUP BY — a alternativa errada da prova escrevia GROUP BY p.ProjNome, AVG(t.Horas).

A sutileza que vale ponto Para "não pode excluir se houver filho" você não escreve nada — apenas declara a FK normal. O comportamento padrão do Oracle já é recusar. Muita gente inventa um "ON DELETE RESTRICT", que não existe na sintaxe Oracle.

Sequence

CREATE SEQUENCE seq_funcionario START WITH 1 INCREMENT BY 1 NOCACHE NOCYCLE;

INSERT INTO funcionario (matricula, nome)
VALUES (seq_funcionario.NEXTVAL, 'ANA');
O que a Q21 cobrou A ordem dos INSERTs importa por causa da FK: a tabela "pai" (DEPARTAMENTO) entra primeiro, a "filha" (FUNCIONARIO) depois. E a FK fica na tabela filha — na FUNCIONARIO, não na DEPARTAMENTO — apontando para a chave (coddep), nunca para o nome.

5Views ED2, Q8 e Q11

CREATE VIEW v_funcionarios_rh AS
SELECT id, nome, salario, nome_depto
  FROM funcionario
 WHERE nome_depto = 'RH'
WITH CHECK OPTION;
Ordem da sintaxe — é o que a Q8 testou O WITH CHECK OPTION vem no final de tudo, depois do WHERE. As alternativas erradas colocavam ele logo após o nome da view ou inventavam WITH CHECK OPTION ON coluna = valor, que não existe.
Quando uma view é atualizável Só dá para inserir/atualizar através de uma view se ela vier de uma única tabela, contiver a chave primária e todos os campos NOT NULL sem default. Não são atualizáveis as views com junção, agrupamento ou função agregada.
A regra da Q11 Quando a view tem uma função agregada, é obrigatório nomear as colunas — ou na lista após o nome da view, ou com AS no SELECT: 
CREATE VIEW proj_media_horas (nome_projeto, media_horas) AS
SELECT p.projnome, AVG(t.horas)
  FROM projeto p, trabalha_em t
 WHERE p.projnumero = t.pnr
 GROUP BY p.projnumero, p.projnome;

6PL/SQL ED2, Q10 e Q14

As três frases que resolvem as duas questões
  • O código PL/SQL é executado dentro do SGBD, não dentro da aplicação.
  • Por rodar no SGBD, o tráfego de rede é reduzido — e é por isso que o desempenho melhora.
  • PL/SQL não é padronizada entre os SGBDs, o que dificulta migrar código de um para outro. (Era a única afirmativa verdadeira da Q10.)
CURSOR É a área de memória usada para processar várias linhas retornadas por um SELECT, uma de cada vez. Era a resposta da Q14 — as outras opções (RECORD, IS TABLE OF, BULK COLLECT, ROWTYPE) existem, mas não são o espaço de memória que percorre linha a linha.

1ª QUESTÃO · JOIN
Enunciado
Quer-se listar todos os clientes, inclusive os que nunca fizeram pedido, mostrando o número do pedido quando existir. Qual consulta atende?
Alternativas
Resposta comentada
2ª alternativa. A palavra "todos" referida à tabela do FROM pede LEFT JOIN. A 1ª e a 4ª são a mesma coisa (INNER) e descartam quem não tem pedido; a 3ª mantém todos os pedidos, não todos os clientes; a 5ª faz produto cartesiano.
2ª QUESTÃO · JOIN
Enunciado
Sobre FROM item_pedido i RIGHT JOIN produto pr ON i.codproduto = pr.codproduto, é correto afirmar:
Alternativas
Resposta comentada
4ª alternativa. O RIGHT preserva a tabela da direita, que aqui é produto. Produto sem venda aparece com NULL nas colunas de item_pedido. A equivalência correta seria produto pr LEFT JOIN item_pedido i — a 2ª troca a palavra e inverte o sentido.
3ª QUESTÃO · JOIN
Enunciado
Um aluno escreveu: FROM cliente c LEFT JOIN pedido p ON c.codcliente = p.codcliente WHERE p.valor_pedido > 50 esperando ver também os clientes sem pedido. O que acontece?
Alternativas
Resposta comentada
3ª alternativa. Para o cliente sem pedido, p.valor_pedido é NULL, e NULL > 50 nunca é verdadeiro — a linha é descartada pelo WHERE. Para manter o comportamento de LEFT, o filtro sobre a tabela opcional precisa ir dentro do ON.
4ª QUESTÃO · NULL
Enunciado
Como verificar, no Oracle, se a coluna observacao está sem valor?
Alternativas
Resposta comentada
1ª alternativa. NULL é ausência de valor e não pode ser comparado com = nem <>. O perigo da 2ª e da 4ª é que elas não dão erro — simplesmente devolvem zero linhas.
5ª QUESTÃO · ALTER TABLE
Enunciado
Uma tabela já possui 500 registros e é preciso acrescentar a coluna tipo, obrigatória. Qual a sequência correta?
Alternativas
Resposta comentada
3ª alternativa. Com a tabela povoada, criar direto como NOT NULL falha — as 500 linhas ficariam sem valor. CREATE criaria outra tabela; INSERT insere linhas, não colunas; UPDATE muda conteúdo, não estrutura.
6ª QUESTÃO · SQL
Enunciado
Com relação à linguagem SQL, é correto afirmar que:
Alternativas
Resposta comentada

9Cola de 1 minuto

JOIN — o essencial

  • INNER = só quem casa dos dois lados
  • LEFT = tudo do FROM + NULL
  • RIGHT = tudo do JOIN + NULL
  • RIGHT = LEFT com as tabelas trocadas
  • "todos os…" → LEFT · "que têm…" → INNER
  • "quem NÃO tem" → LEFT + IS NULL
  • Filtro da tabela opcional vai no ON
  • Sem ON = produto cartesiano
  • Oracle: (+) fica do lado do buraco

NULL e grupo

  • IS NULL, nunca = NULL
  • WHERE filtra linha, HAVING filtra grupo
  • HAVING não é função agregada
  • Agregadas: COUNT, SUM, MAX, MIN, AVG
  • Quem ordena é ORDER BY
  • Coluna fora de agregada → entra no GROUP BY

DDL e FK

  • NOT NULL em tabela cheia → 3 passos
  • CASCADE apaga junto · SET NULL anula
  • "não pode excluir" = não escreve nada
  • FK fica na tabela filha, aponta pra chave
  • INSERT: pai primeiro
  • seq.NEXTVAL gera a PK

View e PL/SQL

  • WITH CHECK OPTION no fim
  • Com junção/agregada → não atualizável
  • Agregada na view → nomear a coluna
  • PL/SQL roda no SGBD, reduz rede
  • PL/SQL não é padronizada
  • CURSOR processa linha a linha
