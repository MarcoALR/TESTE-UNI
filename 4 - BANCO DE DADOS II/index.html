0Como é a prova

A prova do Estudo Dirigido junta várias matérias. A parte de Banco de Dados II teve 7 questões nas duas devolutivas. Cada questão vem numa tabela com Enunciado, Alternativas e, na devolutiva, a Resposta comentada. O simulado desta página usa esse mesmo visual.

Os 4 tipos de questão que aparecem

  1. "Qual comando está correto?" — as 5 alternativas trazem códigos quase iguais. A diferença está num detalhe: a ordem das cláusulas, onde fica o WITH CHECK OPTION, o que entra no GROUP BY, uma coluna sem nome…
  2. Afirmativas I, II, III — você marca "somente I e III", "somente III" etc. Julgue uma afirmativa de cada vez, como verdadeira ou falsa.
  3. Tabela de dados → resultado — mostram os dados de uma tabela e o resultado final, e você escolhe o SELECT que gera aquele resultado (normalmente com GROUP BY, COUNT e SUM).
  4. Discursiva — escrever os comandos (ex.: as chaves estrangeiras com ON DELETE) ou achar os erros de um script.

1Funções de uma linha

Função de linha trabalha em cada linha: entra 1 valor, sai 1 valor. Se a tabela tem 4 linhas, o resultado tem 4 linhas.

Ela pode ir no SELECT (para mostrar) ou no WHERE (para filtrar), e dá para colocar uma dentro da outra, como ROUND(MONTHS_BETWEEN(...), 1).

DUAL = tabela de mentirinha A DUAL tem 1 linha só. Serve para usar uma função sem precisar de tabela: SELECT SYSDATE FROM DUAL;. Se você escrever SELECT SYSDATE FROM funcionario;, a data aparece repetida, uma vez para cada funcionário.

Exemplo completo (tabela FUNCIONARIO do material)

SELECT matricula,
       UPPER(nome)                                  AS nome,
       TO_CHAR(dtadmissao, 'DD/MM/YYYY')            AS data_admissao,
       ROUND(MONTHS_BETWEEN(SYSDATE, dtadmissao), 1) AS meses_de_empresa,
       TRUNC(MONTHS_BETWEEN(SYSDATE, dtadmissao))    AS meses_completos,
       salario + NVL(comissao, 0)                   AS total_remuneracao
  FROM funcionario
 ORDER BY meses_de_empresa DESC;
Pegadinhas
  • ROUND × TRUNC: ROUND(4.567,2) = 4.57 e TRUNC(4.567,2) = 4.56. "Meses completos" é TRUNC.
  • Ordem no MONTHS_BETWEEN: MONTHS_BETWEEN(SYSDATE, dtadmissao) dá positivo. Invertendo as datas, dá negativo.
  • SYSDATE − data dá a diferença em dias, não em meses.
  • NULL numa conta vira NULL: salario + comissao fica NULL quando a comissão é nula. Use salario + NVL(comissao,0).
Teste rápido: SELECT UPPER(nome), LENGTH(nome) FROM funcionario WHERE matricula = 1002; (nome = 'maria santos') Resultado: MARIA SANTOS e 12. O LENGTH conta o espaço: "maria" (5) + espaço (1) + "santos" (6) = 12.

2NULL — valor desconhecido caiu na prova

NULL não é zero nem vazio: é "não sei". E nada é igual a "não sei", nem o próprio NULL.

✗ Errado

WHERE endereco = NULL
WHERE endereco <> NULL
Nunca é verdadeiro, então não retorna nenhuma linha.

✓ Certo

WHERE endereco IS NULL
WHERE endereco IS NOT NULL
"Endereço desconhecido" / "endereço conhecido".

Trocar por um valor

NVL(comissao, 0)
Quando é NULL, usa 0 no lugar.
Onde o NULL aparece em outros assuntos
  • COUNT(coluna) ignora NULL; COUNT(*) conta todas as linhas.
  • AVG(coluna) ignora NULL: divide só pelas linhas que têm valor.
  • NOT IN (subconsulta): se a subconsulta devolver um NULL, a consulta não retorna nada.
  • No Oracle, texto vazio '' é tratado como NULL.

As duas formas de escrever (as duas caem)

Forma "Oracle antiga" (vírgula + WHERE)

SELECT c.nome, p.num_pedido, p.valor_pedido
  FROM cliente c, pedido p
 WHERE c.codcliente = p.codcliente;

Forma ANSI (JOIN … ON)

SELECT c.nome, p.num_pedido, p.valor_pedido
  FROM cliente c
  JOIN pedido p ON p.codcliente = c.codcliente;

c e p são apelidos (alias) das tabelas e servem para escrever menos. Com 3 tabelas, você precisa de 2 ligações; com 4 tabelas, de 3. Regra: N tabelas → N−1 condições de junção.

Produto cartesiano (erro clássico) Sem a condição de junção, o Oracle combina todas as linhas com todas. Com 4 funcionários e 3 departamentos, saem 4 × 3 = 12 linhas sem sentido. Por isso sempre escreva o WHERE ou o ON ligando as chaves.

Veja a diferença: INNER, LEFT e RIGHT

Regra do (+) no Oracle O (+) vai do lado da tabela que pode faltar, ou seja, a que vai aparecer com NULL.
Todos os funcionários, mesmo sem departamento: WHERE f.coddep = d.coddep(+) (equivale a f LEFT JOIN d).
Todos os departamentos, mesmo sem funcionário: WHERE f.coddep(+) = d.coddep (equivale a f RIGHT JOIN d).
Cuidado com o material No texto de JOIN do material, o exemplo WHERE e.coddep(+) = d.coddep aparece como "funcionários sem departamento". Pela regra do Oracle, esse comando traz todos os departamentos, inclusive os sem funcionário. Para trazer todos os funcionários, o (+) fica do lado de d. Se cair na prova, pense na regra: "o (+) fica do lado de quem pode faltar".

Exemplo com 4 tabelas (sua Loja)

-- nome do cliente, pedido, produto e quantidade
SELECT c.nome, p.num_pedido, pr.descricao, i.quantidade_item
  FROM cliente c
  JOIN pedido p       ON p.codcliente  = c.codcliente
  JOIN item_pedido i  ON i.num_pedido  = p.num_pedido
  JOIN produto pr     ON pr.codproduto = i.codproduto
 WHERE c.cidade = 'UBA';
Teste rápido: quando usar DISTINCT num JOIN? Quando a mesma informação pode repetir. Exemplo: "produtos comprados pelo JOAO". Se ele comprou arroz em 2 pedidos, o arroz aparece 2 vezes. Com SELECT DISTINCT, aparece 1 vez só.

4Funções de grupo, GROUP BY e HAVING caiu na prova

Função de grupo pega várias linhas e devolve 1 valor: conta, soma, média, maior e menor.

HAVING não é função! As funções de grupo são só COUNT, SUM, AVG, MAX e MIN. Uma alternativa dizendo "SUM, MAX e HAVING são funções agregadas" está errada (caiu assim).

Regra de ouro do GROUP BY Toda coluna do SELECT que não está dentro de COUNT/SUM/AVG/MAX/MIN tem que estar no GROUP BY.
SELECT c.codcliente, c.nome, SUM(...) → GROUP BY c.codcliente, c.nome.

WHERE × HAVING (a mais cobrada)

WHERE — filtra LINHAS, antes de agrupar

"Só pedidos de 2025", "só clientes de Ubá". Não aceita função de grupo.

HAVING — filtra GRUPOS, depois de agrupar

"Só clientes com total > 1000", "só departamentos com média > 5000". Usa função de grupo.
SELECT codcliente, SUM(valor_pedido) AS total
  FROM pedido
 WHERE data_criacao >= TO_DATE('01/01/2025','DD/MM/YYYY')   -- linhas
   AND data_criacao <  TO_DATE('01/01/2026','DD/MM/YYYY')
 GROUP BY codcliente
HAVING SUM(valor_pedido) > 1000                            -- grupos
 ORDER BY total DESC;

Ordem de ESCREVER × ordem que o Oracle EXECUTA

Você escreve:SELECT→FROM→WHERE→GROUP BY→HAVING→ORDER BY
Oracle executa:FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY

Para decorar a ordem de escrever: "Sem Fé, Walter Gasta Horas Orando". Como o SELECT roda quase no fim, o apelido criado nele não funciona no WHERE, mas funciona no ORDER BY.

Os 3 erros que viram alternativa errada
  • SELECT coddep, nome, COUNT(*) … GROUP BY coddep → ORA-00979: nome não está no GROUP BY.
  • SELECT coddep, COUNT(*) FROM funcionario (sem GROUP BY) → ORA-00937.
  • WHERE COUNT(*) > 2 → ORA-00934: função de grupo no WHERE. O certo é usar HAVING.
Outras pegadinhas (afirmativas)
  • Quem ordena o resultado é o ORDER BY, não o GROUP BY.
  • O DISTINCT não é o padrão: sem ele, as linhas repetidas aparecem.
  • COUNT(*) conta as linhas que satisfazem as condições da consulta (esta foi a correta em 2025).

5Subconsultas (consultas aninhadas)

É uma consulta dentro de outra, sempre entre parênteses. A de dentro roda primeiro e entrega o resultado para a de fora.

Pense em 2 passos: 1º descobrir um valor (o salário do JOAO, a média…), 2º usar esse valor no filtro.

-- "Qual o nome do funcionário que ganha mais que o JOAO?"
SELECT nome
  FROM funcionario
 WHERE salario > (SELECT salario
                    FROM funcionario
                   WHERE nome = 'JOAO');
-- Acima da média (AVG não pode ir direto no WHERE, então vai na subconsulta)
SELECT codproduto, descricao, preco_unitario
  FROM produto
 WHERE preco_unitario > (SELECT AVG(preco_unitario) FROM produto);

  LEFT JOIN pedido p ON p.codcliente = c.codcliente

Erros de subconsulta
  • Usar = quando a subconsulta devolve mais de uma linha → ORA-01427. Troque por IN.
  • Esquecer os parênteses → erro de sintaxe.
  • NOT IN com um NULL na subconsulta → não volta nenhuma linha. O NOT EXISTS não tem esse problema.
JOIN ou subconsulta? Se você precisa mostrar colunas das duas tabelas, use JOIN. Se só precisa filtrar com base em outra tabela, a subconsulta resolve. O material lembra que muitas subconsultas deixam a consulta mais lenta.

6Views (visões) caiu 2 vezes

A view é um SELECT salvo com nome, uma "tabela virtual". Ela não guarda os dados, guarda só a consulta.

CREATE OR REPLACE VIEW vw_pedido_acima_1000 AS
SELECT c.nome AS nome_cliente, c.cidade, p.num_pedido,
       pr.codproduto AS cod_material, pr.descricao AS nome_material
  FROM cliente c
  JOIN pedido p      ON p.codcliente  = c.codcliente
  JOIN item_pedido i ON i.num_pedido  = p.num_pedido
  JOIN produto pr    ON pr.codproduto = i.codproduto
 WHERE p.valor_pedido > 1000;

SELECT * FROM vw_pedido_acima_1000;   -- usa como se fosse tabela
DROP VIEW vw_pedido_acima_1000;       -- apaga só a view, os dados continuam

Para que serve: simplificar (a consulta grande vira um nome) e dar segurança (mostrar só algumas colunas ou linhas).

Coluna com função PRECISA de nome

Se a view tem AVG(...), SUM(...), UPPER(...) etc., essa coluna precisa de nome. Sem nome, o Oracle dá erro (ORA-00998). Há 2 jeitos de dar o nome:

-- Jeito 1: lista de nomes depois do nome da view (foi a resposta correta em 2025)
CREATE VIEW ProjMediaHoras (NomeProjeto, MediaHoras) AS
SELECT p.ProjNome, AVG(t.Horas)
  FROM Projeto p, Trabalha_em t
 WHERE p.ProjNumero = t.Pnr
 GROUP BY p.ProjNumero, p.ProjNome;

-- Jeito 2: apelido dentro do SELECT
CREATE VIEW vw_total_cliente AS
SELECT codcliente, SUM(valor_pedido) AS total_vendido
  FROM pedido
 GROUP BY codcliente;

WITH CHECK OPTION

Ele impede INSERT ou UPDATE pela view de uma linha que ficaria fora do filtro dela. Exemplo: numa view só de RH, não dá para inserir um funcionário de VENDAS.

CREATE VIEW V_Funcionarios_RH AS
SELECT id, nome, salario, nome_depto
  FROM Funcionario
 WHERE nome_depto = 'RH'        -- 1º o filtro
  WITH CHECK OPTION;            -- 2º no FINAL do comando
Formas erradas que aparecem nas alternativas
  • CREATE VIEW v WITH CHECK OPTION AS SELECT… → lugar errado (ele vem no final).
  • WITH CHECK OPTION ON nome_depto = 'RH' → não existe "ON condição"; o filtro vai no WHERE.
  • View com junção ou com GROUP BY → não é atualizável, então o CHECK OPTION não faz sentido nela.
  • ...GROUP BY ...; WITH CHECK OPTION; → o ponto e vírgula antes encerra o comando, e sobra um pedaço solto.
Quando dá para fazer INSERT/UPDATE por uma view (resposta comentada de 2025)
  • A view é de uma tabela só e contém a chave primária e todas as colunas NOT NULL sem valor default.
  • Views com junção de várias tabelas, em geral, não são atualizáveis.
  • Views com GROUP BY / funções de grupo não são atualizáveis.
  • Bônus: WITH READ ONLY no final deixa a view somente para leitura.

7Chave estrangeira com ON DELETE discursiva em 2025

Pergunta que o ON DELETE responde: "se eu apagar o PAI, o que acontece com os FILHOS?"

O pai é a tabela referenciada (lado 1, ex.: PEDIDO). O filho é quem tem a FK (lado N, ex.: ITEM_PEDIDO). O ON DELETE é escrito na FK, ou seja, na tabela filha.

Sem cláusula (padrão = restrict)

FOREIGN KEY (codcliente)
REFERENCES cliente (codcliente)
Apagar um cliente que tem pedidos dá erro (ORA-02292) e nada é apagado.
Use quando a regra for "não pode excluir se tiver…".

ON DELETE CASCADE

FOREIGN KEY (num_pedido)
REFERENCES pedido (num_pedido)
ON DELETE CASCADE
Apagar o pedido apaga também os itens dele automaticamente.
Use quando a regra for "excluir junto".

ON DELETE SET NULL

FOREIGN KEY (cod_tipo_pagamento)
REFERENCES tipo_pagamento
  (cod_tipo_pagamento)
ON DELETE SET NULL
Apagar o tipo de pagamento deixa os pedidos com a FK = NULL, e os pedidos continuam existindo.
A coluna da FK precisa aceitar NULL.

Como fica a resposta da discursiva (modelo 2025)

-- 1) Excluiu funcionário -> exclui os dependentes
ALTER TABLE Dependente ADD CONSTRAINT FK_Dependente_FCPF
  FOREIGN KEY (FCPF) REFERENCES Funcionario (CPF) ON DELETE CASCADE;

-- 2) Funcionário que trabalha em projeto NÃO pode ser excluído
ALTER TABLE Trabalha_em ADD CONSTRAINT FK_TrabalhaEm_FCPF
  FOREIGN KEY (FCPF) REFERENCES Funcionario (CPF);            -- sem cláusula

-- 3) Excluiu departamento -> a FK do funcionário fica NULL
ALTER TABLE Funcionario ADD CONSTRAINT FK_Funcionario_Dnr
  FOREIGN KEY (DNR) REFERENCES Departamento (Dnumero) ON DELETE SET NULL;
Pegadinhas de Oracle
  • No Oracle não existe ON DELETE RESTRICT (ele existe no MySQL e no PostgreSQL). Para restringir, basta não escrever nada, porque esse já é o padrão.
  • No Oracle também não existe ON UPDATE CASCADE.
  • SET NULL não funciona em coluna NOT NULL ou que faz parte da PK (como o num_pedido de ITEM_PEDIDO).
  • Para mudar o ON DELETE de uma FK que já existe: ALTER TABLE t DROP CONSTRAINT nome_fk; e depois cria de novo.
  • Palavras-chave para achar a regra no enunciado: "automaticamente também excluídos" = CASCADE; "não deve ser excluído caso…" = sem cláusula; "deverá possuir NULL" = SET NULL.

9PL/SQL básico caiu em 2025

Não está na ementa deste ED2, mas caiu em 2 questões da prova do ano passado. Vale 5 minutos:

  • PL/SQL = SQL + recursos de programação (variáveis, IF, LOOP).
  • Roda dentro do SGBD, não dentro da aplicação. Por isso reduz o tráfego de rede e melhora o desempenho.
  • Não é padronizada entre SGBDs (é do Oracle), o que dificulta migrar para outro banco.
  • CURSOR = área de memória para processar várias linhas de um SELECT, uma de cada vez.
DECLARE
  CURSOR c_clientes IS SELECT nome FROM cliente;
BEGIN
  FOR r IN c_clientes LOOP
    DBMS_OUTPUT.PUT_LINE(r.nome);   -- processa 1 linha por vez
  END LOOP;
END;

11Discursivas e "ache o erro"

Escreva sua resposta no quadro (é só rascunho) e depois abra a resposta comentada para comparar.

12Cola de 1 minuto

  • NULL: IS NULL / IS NOT NULL. Nunca = NULL.
  • JOIN: PK (lado 1) = FK (lado N). N tabelas → N−1 ligações. Sem ligação = produto cartesiano.
  • LEFT: mantém tudo da tabela escrita antes do JOIN. (+) fica do lado de quem pode faltar.
  • Grupo: COUNT, SUM, AVG, MAX, MIN. HAVING não é função.
  • GROUP BY: tudo do SELECT que não está em função de grupo vai no GROUP BY.
  • WHERE filtra linhas (sem função de grupo). HAVING filtra grupos (com função de grupo).
  • Ordem: SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY ("Sem Fé, Walter Gasta Horas Orando").
  • COUNT(*) conta tudo; COUNT(col) e AVG ignoram NULL.
  • Subconsulta: entre parênteses. Retorna 1 valor → =; retorna vários → IN. "Não tem" → NOT EXISTS.
  • View: não guarda dados. Coluna com função precisa de nome. WITH CHECK OPTION vai no final, depois do WHERE.
  • View atualizável: 1 tabela, com PK e as colunas NOT NULL. Com JOIN ou GROUP BY, não é.
  • ON DELETE na tabela FILHA: CASCADE (apaga junto), SET NULL (fica nulo), sem nada (bloqueia). Não existe RESTRICT no Oracle.
  • Funções: UPPER/LOWER/LENGTH, TO_CHAR/TO_DATE, SYSDATE FROM DUAL, TRUNC(MONTHS_BETWEEN(SYSDATE, d)), ROUND × TRUNC, NVL.
