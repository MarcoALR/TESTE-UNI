1Cliente-servidor questão 1

O backend faz as quatro coisas — recebe, processa, acessa o banco e responde.

CamadaResponsabilidadeOnde roda
Cliente (frontend)Interagir com o usuário, exibir a interfacenavegador · localhost:4200
Servidor (backend)Lógica da aplicação, validação, acesso ao bancoNode.js · localhost:3000
BancoArmazenar e devolver os dadosPostgreSQL / Supabase
As quatro alternativas erradas da questão 1 Todas erram por reduzir o backend a uma única tarefa. A resposta certa é sempre a mais completa:
  • "apenas valida se o usuário está logado" — reduz a autenticação
  • "apenas armazena, sem validação" — reduz a armazenamento
  • "só roteia e repassa para o cliente processar" — reduz a intermediário
  • "mantém a interface atualizada e gerencia estado no navegador" — isso é frontend
Certa: "recebe requisições, processa a lógica, interage com o banco e envia respostas apropriadas".

A questão 2, resolvida em 10 segundos "Recuperar a lista" → GET · "Inserir novo" → POST · "Atualizar existente" → PUT · "Excluir permanentemente" → DELETE. A ordem I–GET, II–POST, III–PUT, IV–DELETE é a natural; as alternativas erradas apenas trocam POST com PUT ou GET com POST de lugar.
A pegadinha da questão 7 Deram um trecho de código e perguntaram o que a rota faz. Dois sinais bastavam: app.put('/clients/:id') e SET name = $1, ... WHERE id = $4. Verbo PUT + comando UPDATE = modificar um registro existente. Não caia na alternativa "adiciona novos clientes" (seria POST + INSERT) nem em "remove" (DELETE).

3Códigos de status questão 5

FaixaSignificaPrincipais
2xxSucesso200 OK · 201 Created · 204 No Content
4xxErro do cliente400 Bad Request · 404 Not Found
5xxErro do servidor500 Internal Server Error
Quando usar cada um
  • 200 — GET que devolveu os dados, ou UPDATE que deu certo
  • 201 — POST que criou algo novo (é o do seu store)
  • 204 — DELETE que deu certo e não devolve corpo (é o do seu destroy)
  • 400 — o cliente mandou dado inválido
  • 404 — o recurso pedido não existe
  • 500 — quebrou no servidor
A confusão que a prova explora 400 ≠ 404. O 400 é "você mandou errado" (formato, campo faltando); o 404 é "não existe". Na questão 5, a afirmação III juntava as duas situações e o gabarito aceitava "400 ou 404". E lembre: erro de cliente é 4xx, de servidor é 5xx — inverter isso derruba a questão inteira.

A resposta da questão 3, palavra por palavra "Os controladores atuam como intermediários. Recebem os dados da requisição (vindos das rotas), delegam a lógica de negócio para a camada de serviços e retornam ao cliente uma resposta adequada, normalmente em JSON. Isso garante separação de responsabilidades, facilitando testes e manutenção."
As alternativas erradas da questão 3
  • "cuidam da persistência, fazendo operações direto no banco" — isso é o repository
  • "definem as regras de negócio, substituindo a camada de serviços" — isso é o service
  • "apenas autenticação" / "apenas configurar middlewares" — reduções falsas

5Escrever a rota questão 4 — discursiva

A prova deu a rota GET pronta e pediu a POST equivalente, mais um exemplo de corpo JSON. Este é o modelo do gabarito:

// o que já vinha pronto no enunciado
app.get('/products', async (request, response) => {
  const clients = await pool.query("SELECT * FROM clients")
  response.json(clients.rows)
})

// a resposta esperada
app.post('/products', async (request, response) => {
  const product = request.body
  const sql = "INSERT INTO product(name,price,stock) VALUES($1,$2,$3)"
  const values = [product.name, product.price, product.stock]
  await pool.query(sql, values)
  response.json({ message: "produto inserido com sucesso" })
})

E o corpo da requisição:

{
  "name": "calça jeans",
  "price": 10,
  "stock": 40
}
Checklist para não perder ponto na discursiva
  • app.post (não get) e a mesma URL do recurso
  • async na função e await no pool.query
  • Ler os dados de request.body
  • Usar $1, $2, $3 e um array values — nunca concatenar string (é o que evita SQL injection, e o professor cobra isso)
  • Responder em JSON
  • Escrever também o exemplo do corpo, que é metade da questão
Detalhe que rende ponto extra O gabarito respondeu com response.json(...) simples, mas o correto em REST para criação é 201: response.status(201).json(...). É o que o seu próprio user.controller.ts faz no store. Se sobrar espaço, escreva assim e justifique.

6Promises e async/await questão 6

async getProdutos() {
  try {
    const response = await firstValueFrom(this.http.get(url));
    return await response.json();
  } catch (error) {
    console.error('Erro ao buscar produtos', error);
  }
}
PeçaPara que serve
async/awaitEscrever código assíncrono de forma sequencial e legível
try/catchCapturar erros (falha de rede, por exemplo) e evitar que a aplicação quebre
firstValueFromConverter um Observable do Angular em Promise
O erro conceitual que a prova planta "O await faz a função parar totalmente a execução do programa até a resposta chegar." — FALSO. O await pausa apenas aquela função; o resto do programa continua rodando. É esse o ponto inteiro do assíncrono. Outras alternativas falsas: "firstValueFrom é síncrono" (não é, devolve Promise) e "o catch reinicia a requisição automaticamente" (não reinicia nada — só trata o erro).
Conexão com o seu backend No Express 4, um erro lançado dentro de uma função async não chega ao middleware de erro com 4 parâmetros — vira unhandled rejection e a requisição fica pendurada. Por isso todo controller async precisa de try/catch ou de um wrapper. Vale como argumento se cair uma discursiva sobre tratamento de erro.

8Simulado — questões reais

Acertos: 0 / 0
1ª QUESTÃO · prova ED2 2025-2
Enunciado
Ao cadastrar um pedido, a requisição vai do cliente para o servidor, que processa os dados, salva no banco e retorna confirmação. Qual alternativa melhor descreve o papel do backend?
Alternativas
Resposta comentada
1ª alternativa. É a única completa. Todas as outras reduzem o backend a uma única tarefa, e a 5ª descreve, na verdade, o frontend.
2ª QUESTÃO · prova ED2 2025-2
Enunciado
I. Recuperar a lista de produtos · II. Inserir novo produto · III. Atualizar produto existente · IV. Excluir permanentemente. Qual a sequência correta de verbos HTTP?
Alternativas
Resposta comentada
1ª alternativa. Recuperar = GET, inserir = POST, atualizar = PUT (ou PATCH, se parcial), excluir = DELETE. As erradas trocam POST com PUT ou GET com POST.
5ª QUESTÃO · prova ED2 2025-2
Enunciado
I. GET recebe os dados corretamente · II. POST cria um recurso com sucesso · III. Cliente envia dados inválidos ou pede recurso inexistente · IV. Erro inesperado no servidor.
Alternativas
Resposta comentada
4ª alternativa. 200 = OK · 201 = Created (algo novo foi criado) · 400/404 = erro do cliente · 500 = erro do servidor. O gabarito aceita "400 ou 404" porque a afirmação III junta as duas situações.
6ª QUESTÃO · prova ED2 2025-2
Enunciado
Sobre o service em Angular que usa async/await com try/catch e firstValueFrom, assinale a correta.
Alternativas
Resposta comentada
1ª alternativa. O try/catch trata falhas (rede, por exemplo) sem derrubar a aplicação. A 4ª é a armadilha principal: o await pausa só aquela função, não o programa inteiro. E firstValueFrom devolve Promise — por isso o await.
7ª QUESTÃO · prova ED2 2025-2
Enunciado
app.put('/clients/:id', ...) com UPDATE clients SET name=$1, age=$2, email=$3 WHERE id=$4. O que essa rota faz?
Alternativas
Resposta comentada
2ª alternativa. Dois sinais bastam: o verbo PUT (atualização, por convenção REST) e o comando UPDATE com WHERE id = $4. Inserir seria POST + INSERT; remover seria DELETE.
3ª QUESTÃO · prova ED2 2025-2
Enunciado
Projeto Node/Express organizado em camadas (rotas, controladores, serviços e modelos). Qual o papel dos controladores?
Alternativas
Resposta comentada
1ª alternativa. O controller é a ponte: recebe os dados da rota, delega ao service e devolve JSON. A 2ª descreve o repository; a 4ª descreve o service. O valor disso é a separação de responsabilidades — facilita teste e manutenção.

9Cola de 1 minuto

Verbos e status

  • GET listar · POST criar · PUT atualizar tudo
  • PATCH atualizar parte · DELETE remover
  • 200 OK · 201 Created · 204 sem corpo
  • 4xx culpa do cliente · 5xx do servidor

Camadas

  • rota → controller → service → repository
  • Controller = só HTTP, nunca SQL
  • Service = regra de negócio
  • Repository = único com SQL
  • Sempre $1, $2 — nunca concatenar

Async

  • await pausa só a função
  • try/catch evita quebrar a aplicação
  • firstValueFrom: Observable → Promise

Angular

  • {{ }} · [ ] · ( ) · [( )]
  • Elemento novo na tela → mexe no HTML
  • Standalone → recurso nos imports
  • ! não verifica nada em execução
Último conselho Abra o seu cruditens/backend antes da prova e leia os seis arquivos na ordem: server.ts → app.ts → routes → controller → service → repository. Metade deste bloco é perguntar o que cada um deles faz.
